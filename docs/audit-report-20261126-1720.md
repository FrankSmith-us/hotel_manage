- **未覆盖范围**（不做通过性背书）：
  - `ReimbursementsPage.tsx` L331–L1526。
  - Dashboard、Employees、Schedules、Leaves、Payroll、Recruitment、Organization、Login 这几个页面组件。
  - `Modal`、`Toast`、`ApprovalTimeline` 组件。

- **总体结论**：
  - **房态维度不适用**：这是一套 HR + 报销 / 备用金系统，schema 里没有房态、库存或房晚相关表，"房态防超卖"维度改为评估资金类资源（借款余额、预算、审批）的并发安全。
  - **主要风险**集中在认证绕过、账务冲销越权、薪资篡改和敏感信息泄露。
  - **做得好的地方**：报销审批和打款用了 `FOR UPDATE` 行锁与状态前置校验；SQL 全部参数化；CSV 有防公式注入处理；JWT 只携带 `userId`，每次请求都从数据库重新加载权限。
  - **薄弱点**：备用金、请假、补编三条审批流没有锁，也不是原子操作；导出、报表、员工档案的数据隔离存在缺口。

### [P0-01] 生产入口默认开启免密切换账号，JWT 密钥有硬编码兜底

- **审查维度**：RBAC 权限安全
- **涉及位置**：
  - [env.ts:L14-L15](../server/src/config/env.ts#L14-L15)
  - [auth.ts:L80-L166](../server/src/routes/auth.ts#L80-L166)
  - [.env.example:L3-L4](../.env.example#L3-L4)
  - [index.ts:L7-L17](../server/src/index.ts#L7-L17)
- **问题描述与风险影响**：
  - `demoRoleSwitch` 在没配置环境变量时默认就是 `true`，`.env.example` 也写的是 `true`，生产入口（MySQL 模式）没有任何保护。
  - 未登录的人可以先调 `GET /api/auth/demo-accounts` 拿到全部用户名，再调 `POST /api/auth/demo-switch {username:"finance"}`，不需要密码就能拿到财务或管理员的 Token。
  - 没配 `JWT_SECRET` 时会退回到写死的 `'yueqi-hotel-ops-dev-secret-2026'`，任何人都能伪造任意 `userId` 的 Token。
- **代码证据**：
  - `demoRoleSwitch: (process.env.DEMO_ROLE_SWITCH || 'true')...`
  - `/demo-switch` 只校验 `is_active`，然后直接 `signToken(Number(user.id))`
- **修复建议**：
  - 生产环境（例如 `NODE_ENV==='production'`，或 `DB_CLIENT==='mysql'` 且未显式开启演示开关）不注册 `/demo-accounts` 和 `/demo-switch`，默认值改为 `false`。
  - 启动时如果没有 `JWT_SECRET`，或者用的是示例值 `change-this-secret-in-production`，直接拒绝启动。

### [P0-02] 报销可关联任意人、任意门店的已放款借款单，冲销账务错乱

- **审查维度**：订单与账务状态机 / 多门店数据隔离
- **涉及位置**：
  - [reimbursements.ts:L573-L582](../server/src/routes/reimbursements.ts#L573-L582)、[L742-L750](../server/src/routes/reimbursements.ts#L742-L750)、[L1204-L1219](../server/src/routes/reimbursements.ts#L1204-L1219)
  - [workflowEngine.ts:L309-L351](../server/src/services/workflowEngine.ts#L309-L351)
  - [advances.ts:L49-L60](../server/src/routes/advances.ts#L49-L60)
  - [ReimbursementsPage.tsx:L240-L249](../client/src/pages/ReimbursementsPage.tsx#L240-L249)
- **问题描述与风险影响**：
  - 创建和编辑报销时只校验借款单 `status==='DISBURSED'` 和余额，**不校验** `advance.applicant_id === user.id`，也不校验 `advance.hotel_id === claim.hotel_id`。
  - 前端获取可选借款单时总会带上 `hotelId`，后端 `tab=available` 一看到 `hotelId` 就返回该门店**所有人**的已放款借款单。`STAFF` 只看本人借款的分支实际上永远走不到，普通员工在正常界面里就能选到同事的借款。
  - 财务打款时会把冲销金额累加到别人的借款单上，甚至将其结清：A 的费用替 B 还了借款，借款台账与实际债务人对不上。
- **代码证据**：
  - `getAvailableAdvanceBalance` 只按 `id` 查询，没有归属条件
  - 打款时执行 `UPDATE cash_advances SET offset_amount = ?, status = ?`，没有校验归属
- **修复建议**：
  - 在创建、编辑、打款三处统一校验：借款单申请人等于报销单申请人，且门店一致。
  - `tab=available` 对 `STAFF` 强制 `applicant_id = 当前用户`，其他角色要求 `hotelId` 在授权范围内。
  - 打款时用条件更新 `WHERE applicant_id=? AND offset_amount + ? <= amount` 兜底。

### [P0-03] 退回到中间审批人后，审批人可改金额和收款账户，系统自动沿用前序审批

- **审查维度**：订单与账务状态机 / RBAC 权限安全
- **涉及位置**：
  - [reimbursements.ts:L723-L728](../server/src/routes/reimbursements.ts#L723-L728)、[L776-L899](../server/src/routes/reimbursements.ts#L776-L899)
  - [workflowEngine.ts:L278-L307](../server/src/services/workflowEngine.ts#L278-L307)
- **问题描述与风险影响**：
  - 单据退回到第 k 步审批人（例如区域经理）时，`PUT /:id` 允许这个**非申请人**重写全部字段，包括 `items` 金额、`payee_account`、`payment_type`、`cash_advance_id`。
  - 重新提交时：第 k 步被自动标记为 `APPROVED`，处理人就是他自己；k 之前的步骤直接复制原审批人的 `acted_by` 和意见。
  - 后果：前序审批人对原金额的同意被"移植"到篡改后的单据上；中间审批人可以把收款账户换成自己的；审计记录失真。
- **代码证据**：
  - L877-L884 复制前序审批：`UPDATE approval_steps SET status='APPROVED', acted_by=?(prev?.acted_by)...`
  - L885-L889 本节点自动通过
- **修复建议**：
  - 被退回的中间审批人只能补充意见或附件，不能改金额、收款信息和借款关联。
  - 金额或收款信息有任何变化，就清空全部历史审批，从第 1 步重新走。
  - 被退回节点不能自动通过。

- **审查维度**：订单与账务状态机
- **涉及位置**：
  - [advances.ts:L242-L306](../server/src/routes/advances.ts#L242-L306)、[L320-L341](../server/src/routes/advances.ts#L320-L341)
  - [leaves.ts:L236-L327](../server/src/routes/leaves.ts#L236-L327)

- **问题描述与风险影响**：

## 4. 核查清单结论

- **多门店数据隔离（`hotel_id`）**：**存在风险**。列表接口大多按范围过滤、JWT 每次从数据库加载权限，这两点做得好。缺口有：
  - `SELF` 范围被当成门店级（P0-05、P1-06）；
  - payees 接口和费用汇总导出不过滤；
  - 导出在权限范围为空时退回全量（P1-05）；
  - 编辑报销和调店不校验目标门店（P1-03、P1-08）。
- **房态并发防超卖**：**不适用**（项目里没有房态或库存模块）。按资金类资源评估为**存在风险**：报销审批和打款有行锁；借款余额占用、备用金、请假、补编审批没有锁（P1-01、P1-02）。
- **订单与账务状态机**：**存在风险**。报销主流程有前置状态校验，但存在：
  - 冲销越权（P0-02）；
  - 退回后可篡改并自动沿用审批（P0-03）；
  - 重复发票不拦截（P1-04）；
  - 入职跳过状态（P1-09）；
  - 请假和薪资口径缺陷（P1-10）。
- **RBAC 权限安全**：**存在风险**。所有业务路由都挂了 `authenticate`，没发现漏挂；申请人不能审批自己的单。但存在：
  - 免密切换和硬编码密钥（P0-01）；
  - 店长自改薪资（P0-04）；
  - 附件无鉴权与 SVG XSS（P1-07）；
  - 大区负责人任意指定（P1-12）。
- **前后端接口一致性**：**部分覆盖，存在风险**。已核对的接口（报销预览、payees、打款、预算、报表、备用金、认证、工作台 kpis）路径、方法、字段一致，`STATUS_META` 覆盖后端全部状态枚举。问题有两处：
  - 前端获取可选借款单总带 `hotelId`，导致后端只看本人借款的分支永远走不到，直接促成 P0-02；
  - 财务入口和导出按钮对所有角色可见（P2-11）。
  - 未读页面不做结论。
